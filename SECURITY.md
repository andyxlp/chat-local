# ChatLocal security requirements and threat model

**Status:** requirements, not a security certification. Treat all requirements S01–S20 as release-blocking unless an explicitly optional feature is disabled and absent. Report vulnerabilities privately to the repository owner; do not publish live credentials or exploit details. Independent review required before public deployment.

## Assets, trust and limits
Assets: local files and metadata, private research/company documents, credentials, browser/keychain/SSH data, command results, local network, app integrity, OAuth grants, local admin controls and availability. Trusted boundary: device owner, installed verified ChatLocal code, OS security, explicitly authorized cloud AI principals. Remote clients, files/URLs, tool arguments, provider identity claims, tunnel requests and upstream code are untrusted until validated. A tunnel is transport, not authorization. Approved AI clients receive returned content; provider privacy/retention and shared/team connector behavior are outside our control. Native commands execute with same-user permissions; a malicious approved client or compromised user account can read/change other files, credentials and network resources. Do not claim absolute prevention.

## Threats and controls

| ID | Threat / mandatory control |
|---|---|
| S01 | Original author/supply chain: no upstream runtime callback, remote management, auto-download or auto-execute; pin dependencies, reviewed releases and documented provenance; no third-party scripts/fonts/telemetry. |
| S02 | Unknown public caller: no tool result, workspace detail, admin page or usable authorization without local owner approval. OAuth registration alone grants nothing. No legacy master, token-in-path, URL query access token, guest or anonymous tool fallback. |
| S03 | OAuth hijack: vetted standards implementation, S256 PKCE, exact registered redirect, canonical issuer/resource/audience, single-use expiring code, client authentication, state handling, authorization response issuer when appropriate; reject malformed or mismatched requests. |
| S04 | Consent impersonation: pending request with local-only approval, matching one-time pairing context/code, displayed redirect origin and client identity verification level; client-supplied names untrusted. Deny unknown/unexpected requests; require exact match, bounded pending TTL and rate limits. |
| S05 | Token theft/replay: opaque CSPRNG tokens, short access TTL (target 15 min), rotating refresh with replay-family revocation, expiry (target 30-day inactivity, 90-day absolute ceiling, validate provider compatibility), atomic durable storage, no plaintext tokens in logs/URLs; secure storage and binding to grant/client/resource. |
| S06 | Revocation bypass: revoke grant/client/token family, close associated streams/sessions, cancel queued tracked work; check grant on every request and before execution. Session IDs are not credentials. No independently valid SSE token. Pause/stop blocks tools immediately even if tunnel fails to stop. |
| S07 | Local admin exposure: separate listener/socket with no admin routes on remote listener, random local auth, strict Host/Origin checks and CSRF protections, no permissive credentialed CORS, CSP, no external UI assets, local secret protected. No AI ability to toggle policy, approve itself or choose unrestricted scope. |
| S08 | Path escape: canonical approved roots, reject traversal and out-of-root absolute paths, realpath/handle validation and symlink protection including nonexistent ancestors; defend against TOCTOU races and hardlink/special-file hazards or fail closed. Revalidate root identity on mount/symlink change. |
| S09 | Sensitive files: always deny file-tool access to app/config/token/socket/update directories and sensitive credential paths (SSH keys, OS keychain/browser stores, etc.); default block common .env/key files and sensitive metadata/search listings; explicit local narrowly scoped exception only for non-app secrets, documented. Do not leak file existence by errors outside authorization. |
| S10 | Mutating tools: read-only denies all mutation including shell, jobs, git side effects, workspace changes and private-network requests; safe atomic writes with conflict/hash checks, path and size bounds, no automatic overwrite of unrelated content. Remote workspace switching cannot expand grant. |
| S11 | Native execution: off by default; timed explicit local elevation. No root/sudo request or auto privilege escalation; run at normal user privilege, scrub inherited app/tunnel secrets, controlled cwd, time/output/job caps, track process groups and cancel on mode downgrade/pause/revoke/stop where possible. Disclose detached processes can survive and native shell is not sandboxed. |
| S12 | Prompt injection/unsafe intent: tool instructions treat file/web content as untrusted, tell AI to explain operation and ask user; server enforces exact local approval for elevated operations independently of agent. Never auto-follow embedded instructions or let AI self-approve. No model classification alone as security control. |
| S13 | Approval replay: bind approval to principal, workspace, policy generation, exact canonical operation+arguments digest, expiry and nonce; atomic single-use; reject changed/expired/replayed request, recheck immediately before execution. No implicit elevation by tool annotation or chat consent. |
| S14 | Network/SSRF: public fetch off initially or restricted explicitly; HTTPS only, port 443, no URL credentials, private/reserved IPv4/IPv6/mapped/special ranges denied, fail-closed DNS, pin actual socket to validated address, preserve TLS host verification, verify every redirect, bounded response/time/redirects. Private network mode separately grants exact host/port/path with local approval; no metadata/loopback/admin/credential endpoints. No general proxy. Native shell networking cannot be constrained by fetch tool policy. |
| S15 | Git/indirect execution: shell-off git status/diff must not execute hooks, pagers, external diff/textconv, fsmonitor, config/includes, malicious gitdirs, filters or other user-controlled programs. Prefer safe internal implementation or strict isolated configuration. Block git internals modification via file tools unless explicit elevated mode. Test repo boundary/symlinks. |
| S16 | Resource abuse: bounded request/header sizes, concurrency, timeouts, rates and map sizes; reject invalid JSON/schema; rate-limit public OAuth/health, preserve approved grants against registration floods; no unauthenticated job/tool work. Backoff and safe recovery, fail closed on corrupt config/store. |
| S17 | Exfiltration/logging: no project contents, tokens, raw commands/arguments containing secrets in audit, telemetry, crash reports or CI. Local metadata audit with redaction, rotation and user deletion. Sanitized diagnostics preview before sharing. Never send automatic reports. |
| S18 | Network exposure: remote listener loopback only, tunnel only to exact port; use provider TLS and explicit canonical hostname. Tailscale Funnel is public; Cloudflare terminates client TLS at provider edge. No inbound router port, no hidden fallback provider, no auto-expose when app starts by default. |
| S19 | Installation/update: user-level signed/notarized binaries where feasible, verified checksums/signatures, pinned official tunnel binaries/install sources, explicit update, review permissions and dependency provenance, no runtime source execution. Migration does not copy insecure tokens/config; opt-in login item, clean uninstall. |
| S20 | Shared grants: default per-client and workspace ceiling, display who and what is granted; global mode may only narrow, not silently expand client ceiling. Multiple clients cannot share job ownership or sessions. Warn that provider-side shared connector credentials may permit other users; owner must configure personal grants and test. |

## Modes and approval model
First-run defaults: remote OFF, no shared folder until explicit choice; Review when enabled, read-only ON, folder protection ON, shell/jobs/private network OFF, public fetch OFF (restricted mode may be enabled for public docs). Edit enables write inside approved workspace only. Run enables native shell only after owner confirmation, default 15 minutes, choices 5/15/30/60 minutes, never indefinitely by default. Background jobs require shell and explicit toggle/grant; jobs have owner, max lifetime, stop action. Advanced folder protection override must not silently grant all existing clients wider scope; owner must approve explicit additional roots/ceiling and see warning. Sensitive app paths always denied by direct tools. Disable shell or read-only restores restrictive mode and cancels tracked job groups. All permission elevations require local action; AI can request but not enact.

When Shell is enabled, default approval is per-command (including start_job), showing full command and target locally, not remote secrets. Optional explicit timed session grant for repeated native commands may be offered only with a second plain-language warning and exact client/workspace/duration. Never present session grant as sandbox; it authorizes all commands that same user could execute. No heuristic allowlist marketed as safe shell. Separate command approval for destructive/high-risk operations even in session mode where deterministically identifiable; cannot reliably detect every dangerous shell sequence, so default remains per-command. No remote execution with read-only.

Private network access, broad roots and sensitive-file exceptions default denied; implement safe narrow grants, no broad toggle that bypasses mandatory blocks. File writes normally do not require per-call approval within Edit mode; overwrite conflict, bulk/destructive changes and unexpected scope require approval. No delete capability assumed from original; if added, explicit local approval and recoverability where feasible.

## Security evidence and remaining risk
Test every S-ID with negative and positive fixtures; no real user data. Review all ingress, token lifecycle, path APIs, subprocess calls, network routes, dependency/install chain and outbound traffic. Record independent reviewer verdict and unresolved findings. No public tunnel on owner workstation before P0/P1 findings closed. A native shell attacker operating with approved access can still access same-user files, read credentials, persist processes and bypass app-level network restrictions; optional separate OS account or sandbox is stronger but not required by owner. A compromised OS/tunnel endpoint/provider or intentionally authorized disclosure is outside guarantees. No security claim for legacy Easy MCP snapshot.
